# RecoverChain Synthetic Dataset Catalog

Generated by `scripts/data_generation/generate_recoverchain_datasets.py`,
fixed seed `20260922`, deterministic (re-running the script reproduces the
same rows and same checksums). Full manifests with column lists, checksums
and per-dataset stats: `recovery_outcome_manifest.json`,
`ethical_edge_cases_manifest.json` in this folder.

## 1. `recovery_outcome` — the genuine recovery target this repo lacked

- **File:** `data/recoverchain/synthetic/recovery_outcome/recovery_outcome.{xlsx,csv}`
- **Rows:** 6,030 (6,000 generated + 30 intentional near-duplicate rows for
  dedup testing, tagged `_dup` in `case_id`).
- **Target:** `recovery_success` — 1 = at-risk amount recovered within a
  **30-day observation window**, 0 = not recovered in that window.
- **Positive rate:** 17.2% (deliberately harder than the app's live demo
  data — this dataset models genuinely at-risk revenue, not a curated
  success-story sample).
- **Split:** temporal on `obligation_created_at` — train (earliest 70%,
  4,221 rows) / validation (15%, 904 rows) / test (latest 15%, 905 rows).
- **Label mechanism:** a documented weighted-logistic combination (see the
  generator's `z = ...` formula) of prior recovery/payment/late rates,
  attempt/recovery counts, amount (log-scaled), obligation age, engagement/
  login/contact signals, dispute flag, payment-method validity, consent/
  suppression state, and a per-domain effect — **plus unmodeled Gaussian
  noise**, so the task is genuinely uncertain, not a lookup table. No
  feature equals or trivially determines the label (checked programmatically
  by the generator's own leakage test: correlation of every numeric column
  with the target stays well under 0.98).
- **Missing values:** 2% of `average_days_to_payment` set to real NaN;
  `-1` sentinel for `prior_*` fields when a customer/obligation has no
  history (same convention as `ar_recovery_v1`/`billing_recovery_v3`).
- **Validated:** schema, leakage, distribution, entity, and (by construction)
  temporal-ordering checks all pass — see the manifest's `validation_status`.
- **Sanity-check training result** (`backend/ml_reconstruction/train_recovery_outcome.py`,
  full detail in `docs/ai_reconstruction/01_TRAINING_RESULTS.md`): Logistic
  Regression reaches **test ROC-AUC 0.845 / PR-AUC 0.561**, clearly above
  the no-fit historical-rate baseline (0.720 / 0.360) and nowhere near a
  suspicious ~1.0 — this is the intended signature of a realistic, non-leaked
  synthetic label.
- **Intended use:** RESEARCH / TRAINING. Synthetic — never presented as
  real customer data. This is the dataset to use if you want to see a
  Recovery Probability Model trained end to end, as distinct from the
  Late Payment Risk Model (`ar_recovery_v1`).

## 2. `ethical_edge_cases` — safety behaviour, not accuracy

- **File:** `data/recoverchain/synthetic/ethical_edge_cases/ethical_edge_cases.{xlsx,csv}`
- **Rows:** 50 (10 hand-specified scenarios A-J from the reconstruction
  brief, each expanded into 5 amount/domain variants).
- **No ML target.** Each row carries `expected_decision`: the **real rule
  name** this repository's actual policy engine
  (`backend/application/policy_engine.py`) or ingestion dedup path produces
  for that situation — cross-checked against the actual rule vocabulary in
  the code (`ContactPermission`, `FinancialAutomatedLimit`,
  `PaymentMaxRetries`, `PaymentRetryCooldown`, `ObligationSettled`,
  `StopRule`, `ActionDomainApplicability`), not an invented expectation.
- **Purpose:** exercise the policy layer's safety behaviour directly —
  consent-false blocks action, suppression blocks action, a low-value case
  with high predicted probability still goes through the same policy check
  (probability never bypasses it), a large uncertain-confidence case
  escalates rather than auto-executing, a duplicate is caught at ingestion,
  an already-recovered obligation is denied further action, an unknown
  outcome stays in verification rather than being marked resolved, a
  low-confidence/anomalous case escalates for review, repeated recent
  attempts trigger cooldown, and a policy-prohibited action is blocked even
  when the model likes it. This is the direct evidence that
  **ML prediction ≠ authorization**.
- **Not used for training or accuracy benchmarking** — using it that way
  would be meaningless; it exists to be run through the live policy engine.
  **Done:** `backend/tests/ml/test_ethical_edge_cases.py` feeds each of the
  10 scenarios through the real `DeterministicPolicyEngine.evaluate()`
  (cases A-D, F, I, J), the real ingestion dedup fingerprint (case E), the
  real lifecycle terminal-state set (case G), and the real anomaly detector
  (case H) — 11 tests, all passing against production code, not a
  re-implementation of it. A guard test also fails loudly if the dataset's
  scenario list and the test file's coverage ever drift apart.

## 3. `action_outcome` — P(recovery | X, action), honestly labeled OBSERVATIONAL_DATA

- **File:** `data/recoverchain/synthetic/action_outcome/action_outcome.{xlsx,csv}`
- **Rows:** 3,000. **Actions:** `RETRY_PAYMENT`, `SEND_PAYMENT_REMINDER`,
  `REQUEST_PAYMENT_METHOD_UPDATE`, `ESCALATE_TO_HUMAN`.
- **Target:** `recovery_success` within a 14-day window; `recovered_amount`
  and `action_outcome` (`RECOVERED`/`NOT_RECOVERED`/`BLOCKED_NO_CONSENT`)
  are consistent with it by construction (validated: `recovered_amount` is
  always 0 when `recovery_success=0`).
- **CRITICAL — this is `OBSERVATIONAL_DATA`, not a randomized experiment.**
  `selected_action` is assigned by a policy-like rule correlated with the
  case's own features (amount, failure reason, prior recovery rate) — not
  random assignment — so action and case difficulty are **confounded by
  construction**, exactly as a real merchant policy would confound them.
  Verified empirically after generation: `ESCALATE_TO_HUMAN` cases average
  ₹3,070 at risk vs. ₹600-700 for the other three actions, and show the
  **lowest** naive recovery rate (21.5%) despite having the largest
  per-action effect coded into the label mechanism (0.40, higher than
  `RETRY_PAYMENT`'s 0.15-0.55) — a textbook illustration of why reading
  "action X recovers less" directly off observational data is biased by
  who got assigned to it, not by the action's real effect. This confounding
  is the point of the dataset, not a flaw to hide.
- **An earlier generator bug (found and fixed before shipping):** the
  original escalation threshold (₹15,000) barely intersected this dataset's
  amount distribution (log-normal, mean ≈ ₹900), so fewer than 2% of
  `ESCALATE_TO_HUMAN` rows were actually amount-driven — the "confounded by
  amount" claim would have been false. Re-set to ₹2,000 (≈90th percentile
  of the actual generated distribution) and re-verified the confounding is
  real before writing this document.
- **Intended use:** `OBSERVATIONAL_DATA` — for offline-policy-evaluation-
  style inspection only (`application/offline_policy_evaluation.py`'s own
  standing rule: predicted association ≠ causal effect). Not causal
  evidence unless the actions were genuinely randomized at collection time,
  which they were not.

## 4. `guide_demo` — upload this through the live app, not just read it

- **File:** `data/recoverchain/synthetic/guide_demo/guide_demo.{xlsx,csv}`
- **Rows:** 147, in the **exact schema the running app's own upload flow
  expects** (`customer_id`, `amount`, `invoice_date`, `status`, `reason`) —
  the same shape as the app's built-in "Use sample data" demo file.
- **`status` values** are drawn from the real ingestion classifier's own
  vocabulary (`api/dataset_router.py`'s `_NOT_FAILED`/`_FAILED` sets) and
  **`reason` values** from the real diagnosis engine's recognized failure
  codes (`application/diagnosis_engine.py`) — so every row produces a real,
  specific diagnosis, not a generic placeholder.
- **Deliberately includes**, by construction: 20 already-paid rows (should
  be skipped at ingestion, never become cases), 80 small failed payments
  (auto-approvable), 30 large failed payments (should escalate), one exact
  duplicate pair, and 15 rows exercising the rest of the status vocabulary
  (`unpaid`/`declined`/`error`).
- **Duplicate-pair behavior, verified against the real running app (not
  assumed):** an exact-duplicate row *within the same upload* is correctly
  treated as two legitimate occurrences, not deduped — the app's
  `occurrences`/`occurrence` counter (`api/dataset_router.py`) is designed
  to allow a customer genuinely failing the same way twice. Real dedup only
  fires against *previously persisted* events. Confirmed live: first
  `generate-cases` run on this file → 127 cases from 147 rows (20 skipped as
  already-paid, the duplicate pair both accepted); re-running `generate-cases`
  on the *same* file → `duplicate_event: 127, cases_created: 0` — every
  previously-ingested row correctly recognized as a duplicate on re-upload.
  This is the accurate, verified teaching point, not the "single-file dedup"
  behavior I originally assumed before actually running it.
- **Intended use:** `DEMONSTRATION` — upload through the running app's own
  UI to walk a guide/professor through the full XLSX → prediction → policy
  → execution → outcome pipeline live, per the brief's own §45 acceptance
  test.
