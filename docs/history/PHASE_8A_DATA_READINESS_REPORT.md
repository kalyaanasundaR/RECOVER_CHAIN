# Phase 8A — Real-Data Readiness, Outcome Collection & Model-Gating

**No model was trained, fitted, tuned, benchmarked, or deployed in this phase.**
This report's success is independent of whether the final decision is GO or
NO-GO — it is NO-GO, and that is the correct, honest answer given the data.

## 1. Executive Summary

Phase 8A made RecoverChain able to **collect, validate, and audit real
recovery outcomes without contaminating them with test data** — the stated
mission — without training anything. Concretely:

- Every outcome event now carries an explicit, closed-vocabulary
  **provenance** field (`production`, `human_confirmed`,
  `payment_provider`, `invoice_system`, `subscription_system`,
  `checkout_system`, or `test`), defaulting to `test` when omitted — never
  silently `production`.
- A new **data-readiness endpoint** (`GET /system/data-readiness`) reports
  real counts, real data-quality issues, real temporal coverage, and a
  real per-task model-readiness gate — all computed from the live database,
  nothing estimated.
- A new **independent root-cause observation** capability
  (`POST /cases/{id}/observed-cause`) lets a human record what actually
  happened, structurally distinct from the deterministic diagnosis engine's
  rule output — closing Phase 7's circular-label finding with a real,
  usable path forward instead of just a diagnosis.
- **Result**: `production_outcomes_count = 0`. Every one of the 16
  outcome-event rows in this dev database (12 distinct cases) is
  `provenance=test`, because every one of them was generated by me during
  Phase 5/6/7/8A verification. All three future model tasks are gated
  **NOT_READY**, with reasons that cite real numbers, not invented
  thresholds.

## 2. Phase 7 Carry-Forward

## 4. Authoritative Outcome Definition

Formalized in `application/outcome_events.py` (unchanged core reconciliation,
Phase 5) plus the new provenance dimension (`application/
outcome_provenance.py`, Phase 8A). Every `outcome_events` row already
carried, from Phase 5: case identification (`case_id`), timing
(`occurred_at`, `ingested_at`), financial state (`amount`, `applied_amount`,
derived `case.recovered_amount`/`outstanding_amount`/`cancelled_amount`),
action context (via the matched case's `recommendation`/`execution_record`),
and result (`match_status`, `effect`, and the case's `current_state`:
`FULLY_RECOVERED` / `PARTIALLY_RECOVERED` / `CANCELLED` / not-yet-recovered
via `PENDING_VERIFICATION`/`CLOSED_NOT_RECOVERED`). The brief's requested
categories (RECOVERED, PARTIALLY_RECOVERED, NOT_RECOVERED, NOT_EXECUTED,
EXPIRED, HUMAN_RESOLVED) were **not** added as new statuses — the existing
`CaseState`/`RecoveryOutcomeStatus` enums already cover every state this
system can actually reach (per the brief's own instruction: "only use
categories that fit the existing domain model"). What Phase 8A adds is the
one missing dimension: **provenance** (§2 below).

## 5. Data Provenance

New closed vocabulary, `application/outcome_provenance.py`:

| value | meaning | currently reachable by any code path? |
|---|---|---|
| `production` | a real, live integration's report | **no** — no live payment gateway/invoicing/subscription/checkout connector exists (MockExecutionAdapter only, unchanged since Phase 5) |
| `human_confirmed` | a person recording what actually happened | **yes** — `POST /cases/{id}/observed-cause` (cause) exists; outcome-level human confirmation goes through the same `provenance` field on `POST /outcomes` |
| `payment_provider` / `invoice_system` / `subscription_system` / `checkout_system` | a specific real system's report | reserved, not reachable — no such integration exists |
| `test` | anything else (default) | yes — the only value every existing dataset/test/verification pathway can honestly claim |

**A structural finding worth stating plainly**: this system currently has
**no way to produce genuine `production` provenance**, because it has no
live external integration at all. This isn't a Phase 8A gap — it's the same
fact Phase 5/6 already disclosed ("execution and settlement are simulated in
a sandbox; no live payment gateway is connected"), now made visible in the
outcome-provenance data model instead of only in a UI footnote.
`human_confirmed` is the one realistic near-term path to genuine evidence
without a live integration — a merchant operator saying "yes, this customer
really paid."

## 6. Production/Test Separation

Enforced at three levels:

1. **Schema**: `outcome_events.provenance` is `NOT NULL`, a closed vocabulary
   (`application/outcome_provenance.normalize_provenance` rejects an
   unrecognised value with a 422, never coerces it).
2. **Default**: omitting `provenance` on `POST /outcomes` resolves to `test`,
   never `production` — verified live and by regression test
   (`test_phase42...::test_1_3`, `test_3_unrecognised_provenance_is_rejected`).
3. **Aggregation**: `production_outcomes_count` and `test_outcomes_count` are
   computed as disjoint query filters (`provenance IN REAL_WORLD_VALUES` vs
   `provenance == 'test'`), so a test row structurally cannot contribute to
   the production figure — verified live (adding a new `provenance=test`
   outcome moved `test_outcomes_count` up by exactly one and left
   `production_outcomes_count` untouched) and by regression test
   (`test_2_7_test_outcome_never_counts_as_production`,
   `test_deleting_test_data_does_not_change_production_statistics`).

Also verified: `outcome_events` has **no mutation endpoint** (`POST` only,
no `PUT`/`PATCH`/`DELETE` route exists) — a finalized outcome is immutable by
construction; a correction would have to be a new, auditable row, exactly as
the brief requires, never an in-place edit
(`test_outcome_events_has_no_mutation_endpoint`).

**What was deliberately NOT added**: a case-level provenance marker. The
brief's Step 2 outcome contract (§F) only asked for outcome provenance; a
`RevenueEvent` already carries `source_type`/`source_ref`
(`API`/`API_BATCH`/`FILE_UPLOAD` + a dataset id) — a different, pre-existing
axis distinguishing how a case was created, not whether its eventual outcome
is real. A case with no real, matched outcome cannot become a training label
regardless of how the case itself originated, so outcome-level provenance is
the binding constraint; adding a second, redundant case-level flag was
judged unnecessary scope for this phase.

## 7. Outcome Quality Audit

`application/data_readiness.run_quality_checks()` runs every check the brief
lists against every real row (missing case ID on a matched row, missing/
impossible timestamp, negative amount, recovered > amount-at-risk, missing
currency, missing action type, duplicate external id, outcome recorded
before the case existed). **Nothing is silently repaired** — every check
only appends a `QualityIssue`, verified by a regression test that inserts a
deliberately negative-amount row and confirms it is still negative after the
check runs (`test_5_6_quality_checks_flag_bad_values_without_repairing_them`).

**A genuine finding from running this against real (test) data**: 9 of the
16 real outcome rows are flagged `outcome_occurred_before_case_existed` —
their `occurred_at` (a backdated, dataset-realistic date like
`2026-08-20`, chosen during Phase 6 dataset design) is earlier than the
case's actual `created_at` (the real wall-clock moment I ran the ingestion
during Phase 5/6 testing, e.g. `2026-09-15T06:56:...`). This is not a
reconciliation bug — Phase 5/6 already proved "outcome before *action*" is a
valid, supported scenario — but "outcome before the *case itself ever
existed*" is a real inconsistency in how I dated my own test fixtures, and
the new check correctly caught it without me having to construct a special
test case for it. It is left exactly as found; a human/future process
decides whether to correct it (irrelevant either way, since none of it is
`production` provenance).

## 10. Root-Cause Label Independence

`application/data_readiness.build_root_cause_label_status()`:

```
rule_derived_diagnosis_count:        396   (every case's diagnosis_engine output)
independent_observation_count:         1   (added live this phase — a real
                                             human_confirmed observation on
                                             case_a37fa855, via the new endpoint)
```

The new `cause_observations` table and `POST /cases/{id}/observed-cause`
endpoint are the schema Phase 7 called for: a place to collect evidence
genuinely independent of the rule. The endpoint structurally rejects
`"diagnosis_engine"` or `"rule"` as if they were an independent source
(`INDEPENDENT_SOURCES` is a closed list: `human_confirmed`,
`payment_gateway_response`, `checkout_system_event`,
`subscription_billing_event`, `invoice_payment_history` — only the first is
reachable today, for the same reason §5 gives). Verified live (a `source:
diagnosis_engine` request returns 422) and by regression test (§18, test 10).
**Root-cause classifier remains NOT_READY**: 1 independent observation is not
a training set, and the rule-derived count (396) must never be used
regardless of its size — this is the same circularity finding from Phase 7,
now with an actual mechanism to eventually escape it.

## 18. Remaining Blockers

1. **Zero production-provenance outcome data exists**, and cannot exist
   until a real integration or sustained real human-confirmation workflow is
   in place. This is the dominant blocker for every modeling task.
2. **No live integration of any kind** backs `payment_provider`/
   `invoice_system`/`subscription_system`/`checkout_system` provenance —
   `human_confirmed` is the only currently-reachable real-evidence path.
3. **Temporal span (35 days, all of it test data) is insufficient** for a
   credible split even setting the provenance question aside.
4. **Root-cause classification remains blocked by circularity**, now with a
   real (but empty-at-scale) escape hatch (`cause_observations`).
5. **The ML environment's native-DLL reliability is still unresolved** (an
   IT/environment matter, unchanged from Phase 7, not touched this phase).

None of these were worked around, relabeled, oversampled, or fabricated past.

## 19. Exact Conditions Required Before Model Development

Stated as real, checkable conditions — not arbitrary numbers dressed as
science:

- `production_outcomes_count` (or a sustained, credible `human_confirmed`
  volume) must be **greater than zero**, and grow to a scale a domain
  statistician would accept for the specific task (the brief's own
  instruction: an unjustified round number is not offered here).
- Temporal span must cover enough real chronological history that a
  train → validation → test split leaves each window genuinely populated
  and each obligation in the test window enough time to reach a real
  terminal outcome (not still pending).
- `cause_observations` must have enough independent rows, per domain, for
  root-cause work to even be attempted — today that is 1.
- The environment's scipy/scikit-learn/xgboost native-DLL blocking (Phase 7,
  §13) should be resolved or worked around through legitimate means (an IT
  allow-list, or a dedicated environment) before any training run is
  attempted, so a training failure can be distinguished from a data problem.

## 20. Final GO/NO-GO Decision

**NO-GO for any model development (Phase 8B or otherwise).**

Infrastructure readiness and data readiness are evaluated separately, as
required:

- **INFRASTRUCTURE READY: YES.** Provenance separation, data-quality checks,
  the readiness report, the model-readiness gate, and an independent
  root-cause observation path all now exist, are tested, and are running
  live against the real database.
- **DATA READY: NO.** Zero production-provenance outcomes, a 35-day span,
  and one independent root-cause observation. This is the correct answer,
  not a failure of this phase's work — the phase succeeds by reporting it
  accurately rather than manufacturing a passing number.

Per the explicit instruction, **Phase 8B is not started, and no model was
trained.** This report is the end of Phase 8A.
